# ClaimOS Intelligence — Ontology Glossary

This document is the canonical reference for the conceptual model underpinning
the Intelligence Layer. Every term below maps onto either an existing table,
a master_options category, or a planned construct introduced by the Sprint 1
ontology migration (028). When code, prompts, or analytics need to refer to
one of these ideas, use the glossary spelling — not a synonym — so the
vocabulary stays consistent end-to-end.

The glossary is intentionally implementation-aware: each entry calls out the
table or category that backs the concept today, so engineers can move from
"what does this mean" to "where does this live" in one step.

---

## Claim

A **Claim** is the full insurance interaction for a single hospital admission,
from pre-authorisation through final settlement. In storage it is anchored to
an `ipds` row (the inpatient admission), with `insurance_submissions` rows
representing each outbound interaction with the insurer. A claim has exactly
one admission and one patient, but may span multiple submissions (initial
pre-auth, enhancements, query responses, final claim) and multiple insurer
outcomes over its lifetime. The Intelligence Layer treats a claim as the unit
of analysis for outcome prediction, deduction-risk scoring, and document
sufficiency checks. References elsewhere to "case" or "admission claim" mean
the same thing — prefer "claim".

## Stage

A **Stage** is the workflow state of a claim within ClaimOS — distinct from
what the insurer thinks. Stages live on `ipds.stage` (migration 024) and
follow a directed flow: intake → pre-auth-drafting → pre-auth-sent → query →
approved → admitted → discharge → claim-filed → settled. Stages drive the
patient-detail header pill, the deficiency queue, and routing to the right
operator. Transitions between stages are append-only events on
`submission_events` with `event_type = 'stage_changed'` (migration 027). The
"stage_transition_pattern" KB pattern type mines this history for typical
durations and out-of-order anomalies.

## Document

A **Document** is a single file uploaded to or generated by ClaimOS that
participates in a claim — discharge slip, OT notes PDF, insurer query
letter, etc. Each document is classified into one **doc_category**, the
controlled vocabulary seeded in `master_options` (migration 028). The
canonical list mirrors the FE `FIELD_NAMES` map in `PatientPhotosModal` plus
additional pre-auth/claim-stage buckets. Documents have raw storage (S3 key)
plus metadata (upload source, hospital, claim, page count) and act as the
parent for one or more DocumentSections and DocumentExtractions. A document
is immutable once uploaded; corrections happen via new versions, not edits.

## DocumentSection

A **DocumentSection** is a logically distinct slab inside a single Document —
e.g. the "History of Present Illness" block of an admission note, or page 3
of a multi-page final bill. Sections are produced by the document
pre-processor (layout analyser plus heuristics) and exist so extractions can
be anchored to a specific span rather than the whole file. Each section
carries its page range, a section_type label, and a stable hash that survives
re-extraction runs. Downstream features that need provenance — "where did
this value come from?" — point at a DocumentSection, not just a Document.
Sections are derived data: re-runnable, not authoritative.

## DocumentExtraction

A **DocumentExtraction** is a structured value pulled from a Document or
DocumentSection by the LLM extraction pipeline, conforming to the
`document_field_schemas` spec for that doc_category. Each extraction carries
field_key, value, confidence, the source DocumentSection, and the model
version that produced it. Extractions are versioned and never overwritten;
human corrections are stored as a separate "verified" extraction that
supersedes the model output. The review-and-correct UI is driven entirely by
the schema definitions in `document_field_schemas`, so adding new fields
requires only a row insert and prompt update — no code change.

## Procedure

A **Procedure** is the clinical intervention being claimed — a CABG, a
hernioplasty, a routine angiography. ClaimOS resolves the surface form
("CABG done w/ 4 grafts") to a canonical procedure code via
`concept_aliases` (concept_category='procedure'), with the canonical list
sourced from the tariff master and panel-specific procedure lists. A claim
may carry multiple procedures (primary plus secondary). The procedure drives
the expected tariff, the room-category eligibility, and the package
boundaries that show up later as deduction_reason='outside_package'.

## Diagnosis

A **Diagnosis** is the clinical condition justifying the admission and
procedure. Diagnoses are captured as free text on the admission notes and
diagnosis_summary documents, then resolved to ICD-10 codes via
`concept_aliases` (concept_category='diagnosis') and an upstream ICD service.
A claim has one primary diagnosis plus zero or more comorbidities; the
diagnosis_summary `document_field_schemas` spec encodes which fields the LLM
should pull. Diagnosis mismatch between documents (e.g. discharge slip vs
pre-auth) is one of the most common insurer queries, surfaced as
deficiency_type='diagnosis_mismatch'.

## Insurer

An **Insurer** is the entity ultimately paying the claim — Star Health, HDFC
Ergo, Care Health, and so on. Insurers are modelled in ClaimOS via the
`panels` table (one row per insurer-or-TPA the hospital deals with) plus
per-panel attributes (`panel_attributes`, `panel_default_attributes`). For
ML/analytics purposes "insurer" and "panel" are often used interchangeably,
but a panel can also represent a TPA fronting multiple insurers — see Panel.

## Panel

A **Panel** is the (insurer or TPA) endpoint the hospital actually
corresponds with. Panels are configured per hospital and carry routing
metadata (email lists, interface_id, claim submission route) plus reference
data (tariff schedule, room-rent cap, package list). The Intelligence Layer
treats panel as the primary segmentation axis for query-likelihood and
deduction-risk models, because per-panel behaviour varies far more than
per-insurer behaviour. New panels are onboarded through the superadmin UI;
panel-level attribute definitions live in `panel_attribute_definitions`.

## Outcome

An **Outcome** is the insurer's response to a specific submission — approved,
partially approved, queried, rejected, enhancement approved, etc. The
controlled list is the `insurer_outcome` master_options category (migration
028). Outcomes attach to `insurance_submissions` rows (one current outcome
plus history via `submission_events`). Outcome is intentionally separate
from Stage: a submission can have outcome='queried' while the parent claim's
stage is 'query' — the outcome describes what the insurer said, the stage
describes what we're doing about it.

## Query (aka Deficiency)

A **Query** — also called a **Deficiency** when surfaced internally — is the
insurer asking for something before they will approve. Each query carries one
or more deficiency_type codes (`deficiency_type` master_options), the raw
insurer query letter (a Document with doc_category='insurer_query_letter'),
and a derived list of which missing or mismatched items triggered it. The
"insurer_query_pattern" KB type captures recurring query templates by panel
so the system can predict-and-prevent the next one. "Query" is the
insurer-facing term; "Deficiency" is what the ops team sees in their queue.

## Deduction

A **Deduction** is money the insurer cut from the requested amount when
approving. Each deduction has an amount, a deduction_reason
(`deduction_reason` master_options — room_rent_cap, sublimit_breached,
outside_package, etc.), and optional line-item detail tying it back to a
specific bill row. Deductions roll up to a "shortfall" figure per claim that
the hospital may absorb, contest, or pass to the patient. The
"deduction_pattern" KB type mines historic deductions per (panel, procedure)
so the Intelligence Layer can warn at pre-auth time when a request is likely
to be partly cut.

## Tariff

A **Tariff** is the agreed price schedule between a hospital and a panel for
each procedure / room category / consumable. Tariffs live in their own table
(loaded from panel-supplied PDFs and operator-edited where needed) and act as
the reference truth for "what should this claim be worth?". Tariff lookups
power both the procedure_estimate generator and the deduction predictor —
when actuals fall outside tariff, that's an amount_variance_pattern signal.
Tariffs change over time; the schema carries effective_from / effective_to
windows so historic claims compare against the rate that was live at
admission.

## Approval

An **Approval** is an insurer outcome where money was authorised — fully or
partially — for the claim. Approvals are a specialisation of Outcome and
carry the approved amount, room-category authorised, validity window, and a
reference to the source insurer_approval_letter Document. A claim may
accumulate several approvals over its life (initial pre-auth, enhancements,
final settlement). The delta between requested and approved is the
deduction; the delta between approved and billed is the variance the
Intelligence Layer tracks for amount_variance_pattern.

## KbPattern

A **KbPattern** is an entry in the Knowledge Base — a reusable insight mined
from historic claims or hand-authored by ops. Every KbPattern declares one
kb_pattern_type (insurer_query_pattern, deduction_pattern, doc_correlation,
stage_transition_pattern, amount_variance_pattern) plus a JSON body whose
shape is defined per type. KbPatterns are the bridge between raw history and
predictive features: extraction pipelines query them at runtime ("is this
panel known to deduct on this procedure?") and the dashboard surfaces them
to ops ("3 of the last 5 claims to Star Health on this procedure were
queried for missing ICP"). Patterns are versioned and reviewable.

## ClaimDossier

A **ClaimDossier** is the assembled bundle of everything ClaimOS knows about
a claim at a moment in time — claim metadata, every Document with its
extracted fields, all submissions and their outcomes, deductions, queries,
and the KbPatterns currently considered relevant. The dossier is the
canonical input to any downstream reasoning step (LLM prompt construction,
deficiency check, deduction prediction). It is computed on demand from the
underlying tables — there is no `claim_dossiers` table — and cached for the
duration of a single workflow run. Treat the dossier as the unit of
"complete claim context".

## Cardinality cheat sheet

| Parent           | Child                | Cardinality | Notes |
|------------------|----------------------|-------------|-------|
| Claim            | Stage                | 1 : 1 (current) + N (history via submission_events) | Stage transitions are append-only |
| Claim            | Document             | 1 : N       | Documents are immutable once uploaded |
| Claim            | Procedure            | 1 : N       | One primary, zero or more secondary |
| Claim            | Diagnosis            | 1 : N       | One primary, zero or more comorbidities |
| Claim            | Insurance Submission | 1 : N       | Initial, enhancement, query response, final |
| Claim            | Outcome              | 1 : N       | One per submission, plus history |
| Claim            | Query                | 1 : N       | Each query → 1..N deficiency_type codes |
| Claim            | Deduction            | 1 : N       | Each on the final approval, one deduction_reason each |
| Claim            | Approval             | 1 : N       | Pre-auth, enhancements, final settlement |
| Document         | DocumentSection      | 1 : N       | Derived; re-runnable |
| Document         | DocumentExtraction   | 1 : N       | One per field, versioned |
| DocumentSection  | DocumentExtraction   | 1 : N       | Provides provenance anchor |
| Panel            | Tariff               | 1 : N       | Per (procedure × room) with effective_from / to |
| Panel            | Claim                | 1 : N       | A panel is touched by many claims |
| Insurer          | Panel                | 1 : N       | Insurer may appear under multiple TPAs |
| Concept (master) | Alias                | 1 : N       | concept_aliases table |
| doc_category     | Field Schema         | 1 : N       | document_field_schemas, versioned |
| KbPattern        | Claim                | N : N       | Patterns surface across many claims |
| ClaimDossier     | Claim                | 1 : 1       | Dossier is the assembled view of one claim |
